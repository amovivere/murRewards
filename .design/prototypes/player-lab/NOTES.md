## Что смотрел в реальном коде

`.design/prototypes/react-app/src/features/music/MusicPage.jsx` (реальный React-прототип):

- строка 368: кнопка «Следующий трек» → `action('music_skip')`;
- строка 369: кнопка «Пропустить трек» → `action('music_skip')`;
- тост после любой из них: «Трек пропущен» (строка 271).

Итог: сегодня «следующий» и «пропустить» — одно действие с одинаковыми последствиями
(и одинаковым тостом). Стример не может «просто переключить» трек, не отменив заявку,
а зритель не получает ни возврата баллов, ни объяснения. Это и разведено в концепте.

## Семантика: «Следующий трек» vs «Пропустить»

| | **Следующий трек** (`next`) | **Пропустить** (`skip`) |
|---|---|---|
| Смысл | Плеер переходит к следующей заявке | Модератор **отменяет** текущую заявку |
| Баллы | Списаны, заявка считается выполненной | Возвращаются зрителю (по умолчанию, переключаемо) |
| Статус трека | `played` / `completed` | `skipped` / `cancelled` + причина |
| Причина | Не нужна | Обязательна: не та песня / нет звука / правила / битая ссылка |
| Ссылка | Остаётся рабочей | Может попасть в блок-лист, чтобы повторно не заказали |
| Кто делает | Стример (навигация), доступно всегда | Модератор (компенсация), с подтверждением |
| Обратимость | Undo не нужен — это штатный ход | Undo 5–6 секунд + запись в журнал |
| Журнал | `Завершён досрочно: <track>` | `Пропуск: <track> · причина · возврат N баллов @user` |
| Нажатие | 1 клик | Диалог: причина + возврат + блок-лист → подтверждение |

Правило для интерфейса: **«Следующий» — это навигация, «Пропустить» — это компенсация.**
Поэтому у «Следующего» иконка `⏭` и нейтральная secondary-кнопка, у «Пропустить» — `⊘`
и danger-ghost, плюс подписи-пояснения под транспортом (в A) и карточка разницы (в B).

### Предлагаемый контракт с бэкендом

```text
music_next                                  # закрыть текущий как played, включить следующий
music_skip { reason, refund: bool,          # снять заявку, вернуть баллы, причина в журнал,
             block: bool }                  #   опционально добавить ссылку в блок-лист
music_undo_skip { id }                      # вернуть пропущенный трек (в течение 6 с)
music_add_manual { url }                    # ручная заявка (уже есть)
music_remove_item { id, refund: true }      # убрать из очереди с возвратом (уже есть)
```

`music_skip` сейчас меняет очередь без причины/возврата — в новой версии это отдельная команда,
и UI не должен звать её из кнопки «Следующий».

### Крайние случаи, которые концепт уже показывает

- Пропуск во время загрузки: загрузка отменяется, баллы возвращаются, причина пишется.
- Пропуск последнего/единственного трека: очередь пуста → «Ничего не играет» + журнал.
- Ошибка `yt-dlp` (видео недоступно): строка очереди в состоянии `error` с кнопкой «Повторить»;
  баллы не списываются, пока трек не начнёт играть.
- `next` на последнем треке: очередь пуста → плеер останавливается, стример видит пустое состояние.
- Undo пропуска: возвращает трек и его позицию, следующий трек возвращается в начало очереди.

## Функции вокруг музыки (10–15, без фантастики)

| # | Функция | Что делает | Зачем стримеру | Приоритет |
|---|---|---|---|---|
| 1 | **Разделение «Следующий» / «Пропустить»** | next — навигация, skip — отмена заявки с причиной и возвратом баллов + undo | Убирает сегодняшний баг «одна команда на две кнопки», снимает конфликт со зрителем | **P0 / MVP** |
| 2 | **Прозрачные состояния очереди** | Для каждой заявки: в очереди / загрузка (64%) / готов / играет / ошибка с «Повторить» | Стример видит, чего ждёт эфир, и не запускает «мёртвый» трек | **P0 / MVP** |
| 3 | **Удаление из очереди с возвратом баллов** | × в строке → баллы возвращаются, журнал фиксирует | Быстрая уборка без похода в Twitch-награды | **P0 / MVP** |
| 4 | **Хоткеи стримера** | Space, Shift+→, S, ←/→, M, ↑/↓ | Не уводить мышь в OBS/игру во время эфира | **P0 / MVP** |
| 5 | **Журнал музыкальных событий** | Принята/загружена/играет/пропущена/возврат/ошибка | Разбор «почему не сыграло» без логов приложения | **P1** |
| 6 | **Блок-лист ссылок** | Заблокированная ссылка/видео не принимается в заявку, причина | Защита от повторных «шуток» и битых ссылок | **P1** |
| 7 | **Кулдаун и лимиты** | 1 заявка в N минут на зрителя, не больше K треков в очереди | Чтобы один зритель не занимал весь эфир | **P1** |
| 8 | **OBS-оверлей со состоянием** | «Сейчас играет», загрузка/пауза, следующий трек, настройка позиции/шрифта | Зритель понимает, что происходит и сколько ждать | **P1** |
| 9 | **Проверка ссылки до очереди** | yt-dlp: доступность, длительность, возраст; отказ с понятным текстом | Не тратить эфирное время на «видео недоступно» | **P1** |
| 10 | **Ограничение длительности трека** | Обрезка/запрет треков длиннее N минут | Длинный трек не съедает эфир | **P2** |
| 11 | **Статистика эфира** | Сыграно/пропущено/возвращено баллов/среднее ожидание | Понять, что заявки работают, и хвастаться метрикой | **P2** |
| 12 | **Несколько наград-музык / сцены** | Разные пулы очередей: «музыка», «алерты», «сцена X» | Разделять эфирные блоки и темы | **P2** |
| 13 | **AutoDJ при пустой очереди** | Fallback-плейлист, когда заявок нет | Эфир не молчит в паузах | **P2** |
| 14 | **Голосование чата за следующий трек** | `!vote` за один из треков очереди | Вовлечение зрителей, честная очередь | **P3 / потом** |

P0 — то, что закроет боль из текущего бага и ручного теста; P1 — следующий спринт; P2 — после стабилизации; P3 — эксперимент.

## Варианты компоновки

- **A · Stage** — «сцена»: крупный винил/обложка, крупный трек, большие кнопки, очередь справа,
  журнал и статистика снизу. Хорошо для 1400+ ширины и второго монитора.
- **B · Console** — «пульт»: компактный плеер сверху, очередь как таблица заявок с действиями,
  карточка «Правила и модерация» с разницей кнопок, блок-лист и журнал рядом. Хорошо для 980-1200
  и режима «стример разбирает заявки».

Рекомендация: взять **A как основной экран «Музыка» и добавить в него карточку правил из B**;
B оставить как компактный режим для 980×680 и для быстрой модерации во время эфира.
