## 2. Архитектура и поток кадров

### 2.1 `impl eframe::App::update` (app.rs:3496–3591)

Каждый вызов update выполняет:

1. `ViewportCommand::Decorations(false)` — один раз (3499–3502).
2. `resize_edges(ctx)` — хит-тест краёв окна, `ctx.pointer_hover_pos` (3503, 1137–1167).
3. Обработка `close_requested`: сохранить/скрыть в трей/`save_now` (3504–3513).
4. `poll_tray` (3515).
5. `hide_on_start`, контроль доступности трея (3516–3536).
6. `self.poll_audio()` **дважды подряд** (3538 и 3540), между ними `poll_normalize` (3539).
7. `poll_twitch` (3541), `poll_eventsub` (3542), `poll_music` (3543).
8. `playback_state.lock()` + `state.sync(&settings)` — каждый кадр, в т.ч. пересборка `HashMap` со `String` (3544–3546).
9. `poll_eventsub()` **второй раз** (3547), `maybe_save` (3548).
10. Раз в 800 мс при открытой вкладке «Журнал»: `self.logs = logger.entries()` (3550–3553).
11. Отрисовка панелей: `sidebar` (236 px), `title_bar` (38 px), `header`, `footer`, `CentralPanel` с выбранной вкладкой; «Музыка» обёрнута в `ScrollArea` (3555–3578).
12. Модальные окна OBS/редактора/удаления (3581–3585).
13. **Единственный вызов repaint во всём проекте** (3587–3589):
    ```rust
    if self.busy() { ctx.request_repaint_after(Duration::from_millis(150)); }
    ```

### 2.2 Политика repaint: `busy()` (app.rs:294–307)

`busy()` истинно, если: играет звук, есть toast, есть отложенное сохранение, не истёк `wake_until` (1,2 с после `touch()`), открыта вкладка **«Журнал»**, открыта вкладка **«Музыка»**, Twitch в состоянии Busy/Waiting, EventSub Connecting, **`!self.window_visible`**. В этих состояниях — 6,67 кадр/с. Иначе egui ждёт ввода и **`update()` не вызывается вообще** (нет ни одного `request_repaint()` из фоновых потоков — grep по `src` даёт только app.rs:3588).

Следствия:

* «Страховочный» режим включён на вкладках «Журнал»/«Музыка» **даже когда ничего не происходит** → постоянная перерисовка 6,7 кадр/с, пока открыта вкладка.
* В трее: окно не скрывается по-настоящему, а уводится за экран (`window_ops.rs:40-57`, `SetWindowPos(-32000,-32000)`, `WS_EX_TOOLWINDOW`), оставаясь видимым для Windows; `!window_visible` заставляет repaint 150 мс **бесконечно**. Это и есть 2–4 % холостого CPU в трее.
* Пока окно видимо и не busy, `update()` не вызывается → `poll_twitch/poll_eventsub/poll_music` не работают без пользовательского ввода. В частности, **заявка на музыку инициируется только из UI-потока** (`handle_redemption` → `self.music.request`, app.rs:769–795), поэтому при видимом простаивающем окне заявка может «повиснуть» до первого движения мыши. Пока окно в трее (busy) это маскируется 150-мс циклом.
* Нет механизма «разбудить UI» из EventSub/Twitch/трея/музыки: каналы опрашиваются только внутри кадров. Это архитектурный корень и проблем латентности, и костыля с 150 мс.

### 2.3 Механика скрытия в трей и рассинхрон

* `hide_to_tray()` (window_ops.rs:40–57) — окно за экраном, `window_visible=false` в приложении (app.rs:319–324). На закрытие окна (`close_to_tray`) — `CancelClose` + `hide_to_tray` (app.rs:3504–3513).
* Кнопка «Свернуть в трей» в настройках использует **другой** механизм — `ViewportCommand::Visible(false)` (app.rs:2428–2435). По комментарию в window_ops.rs:1–6, при настоящем скрытии eframe «перестаёт присылать обновления» — тогда `update()` не будет вызываться вовсе, а `poll_tray` не сможет обработать событие; спасением является лишь то, что поток трея сам вызывает `ShowWindow` (tray.rs:249–251, 285–288). Это скрытый баг/риск (см. R-2).
* **Рассинхрон (воспроизведён):** при запуске второго экземпляра `main.rs:110–133` → `show_existing_window()` → `window_ops::show_from_tray()` (main.rs:142–144) окно показывается **без** события трея, поэтому в работающем экземпляре `window_visible` остаётся `false`. В журнале нет «Окно открыто из трея», а busy() навсегда истинен; замер на пустой вкладке «Награды»: 1,87 % CPU одним UI-потоком (скриншот подтверждает: видимое окно, 0 играющих звуков, config/лог не меняются).
* Смену видимости из ОС/другого процесса приложение в принципе не отслеживает.

* Текстуры и шрифты не пересоздаются: шрифты Inter грузятся один раз (`theme.rs:73–108`), текстур в UI нет (иконки рисуются painter'ом, `icon.rs` — один раз при старте).

## 3. Находки

Формат: **ID — ссылка — проблема → решение → эффект/проверка**. P = приоритет (P0 — делать сразу, P1 — плановый, P2 — рефакторинг).

### A. Поток кадров и repaint

**F-1 (P0) — busy() держит repaint 6,7 кадр/с в трее и на вкладках «Музыка»/«Журнал».**
`app.rs:294–307`, `app.rs:3587–3589`. Замер: 40 с в busy-состоянии — 4,2 % одного ядра; в простое с видимым окном — 0,4–0,6 %.
→ Убрать `!self.window_visible` и `tab == Log/Music` из `busy()`. Вместо этого: (а) передать `egui::Context` (Clone + Send + Sync) в сервисы (EventSub/Twitch/музыка/трей) и вызывать `ctx.request_repaint()` при появлении события; (б) оставить страховочный heartbeat 1 с (вместо 150 мс) только пока EventSub/Twitch подключены, и 200–250 мс — только пока реально играет музыка/звук. Для вкладки «Журнал» repaint нужен лишь при появлении новой записи (логгер может дёргать ctx).
→ Ожидаемо: трее/простой — **с 2–4 % до <0,3 %** одного ядра; на вкладках — с 1,5–2 % до 0,1–0,3 %. Проверка: 60-секундный замер `Get-Process CPU` в каждом состоянии до/после.

**F-2 (P0) — Рассинхрон `window_visible` после восстановления окна вторым экземпляром.**
`main.rs:142–144` → `window_ops::show_from_tray()`; `app.rs:311–324` обновляет флаг только по событиям трея. Воспроизведено в 22:30:47/22:31:55: окно видно, а busy() истинен → 1,87 % CPU на пустом экране.
→ Не хранить отдельный флаг, а определять видимость в момент восстановления: самый простой путь — в `show_from_tray()` (вызываемом из второго процесса через `WM_APP`/именованное событие) уведомлять работающий экземпляр; надёжнее — полностью убрать `!window_visible` из busy() (следствие F-1) и добавить 1-с heartbeat, тогда рассинхрон перестаёт влиять на CPU. Также добавить в трей-поток вызов `ctx.request_repaint()` после `ShowWindow`.

→ Либо реализовать сохранение: `Queue::save` после каждого изменения (debounce), восстановление в `MusicService::spawn` при `restore_queue=true`, `clear_finished()` раз в N завершённых с сохранением `restore_queue`; либо удалить мёртвый код и настройку из UI. Второй вариант — минимальный, первый — полезный (стримеру важно не потерять оплаченные заявки).
→ Ожидаемо: предсказуемая память (items ограничен), восстановление очереди; проверка: перезапуск во время очереди.

**F-24 (P2) — `ytdlp_update_days` — мёртвая настройка.**
`config.rs:70` — нигде не используется; yt-dlp никогда не обновляется автоматически. При поломке YouTube-извлечения музыка просто перестанет работать до ручного обновления.
→ Либо реализовать (раз в N дней `yt-dlp -U` в фоне, `YtDlp::update` уже есть, ytdlp.rs:206–219), либо убрать настройку из UI/конфига.
→ Надёжность; проверка: журнал.

### E. Память

**F-25 (P2) — `logging::entries()` и Snapshot клонируются многократно; очередей с неограниченным ростом нет (кроме истории Queue.items).**
Подробности в F-6, F-7, F-23. Отдельно: `audio::Status` клонируется в `poll_audio` (дважды за кадр, audio.rs:221–226 + app.rs:3538/3540), `take_errors` аллоцирует `Vec` каждый кадр (audio.rs:229–234) — мелочь, но в горячем пути.
→ Один `poll_audio` за кадр; `take_errors` возвращать `Vec::new()` только при непустом списке (сейчас `mem::take` пустого Vec не аллоцирует — ок).
→ Эффект: мелкий.

**Оценка роста памяти:** журнал 400 записей (~100–200 КБ), кэш треков — только текущий+prefetch (≤64 МБ байт + до ~40 МБ PCM), очередь — несколько КБ + история; утечек не обнаружено. ### F. Сборка, конфиг, безопасность, ошибки

**F-26 (P1) — `default_fonts` у eframe не нужен; шрифты Inter 0,83 МБ + дефолтные.**
`Cargo.toml:19` (`features = ["default_fonts","glow"]`), `theme.rs:64–65` (Inter-Regular 411 640 Б + Inter-SemiBold 419 744 Б). `FontDefinitions::default()` с фичей `default_fonts` подтягивает ~0,4–0,5 МБ стандартных шрифтов egui, которые затем заменяются/не используются (Proportional/Monospace переопределены, но дефолтные данные остаются в бинарнике). Также `lto="thin"` и отсутствие `panic="abort"`.
→ Убрать `default_fonts` (оставить только Inter), добавить `panic = "abort"` в `[profile.release]`, при желании `lto = "fat"` и `opt-level = "s"` для размера; сабсеттинг Inter (латиница+кириллица) даст ещё ~300–400 КБ. Ожидаемый размер: −0,6…−1,0 МБ от 10,77 МБ. Проверка: `cargo build --release`, сравнить размер/поведение.
→ Функционально не влияет.

**F-27 (P2) — Профиль release в порядке; сборка без танцев.**
`Cargo.toml:65–69`: opt-level=3, lto=thin, codegen-units=1, strip=true — это правильные настройки. `eframe` без wgpu (glow) — меньше бинарник и зависимостей. `reqwest` blocking+tls, `tungstenite` native-tls — TLS через Schannel (`schannel.DLL` в списке модулей). Замечание: одновременно `windows = 0.58` (SMTC) и `windows-sys = 0.59` — две разные обёртки WinAPI (небольшой размер, но можно унифицировать при случае).

**F-28 (P2) — Безопасность: DPAPI/TLS — хорошо; два слабых места.**
Хорошо: токены шифруются DPAPI (`secure_store.rs:17–98`), в config только hex; Client Secret не нужен; оверлей слушает 127.0.0.1; TLS включён по умолчанию; `looks_like_secret` (logging.rs:176–178) — грубая защита.
Плохо:
1. В `http.rs:97–103` ошибка `reqwest::Error` конвертируется в строку, которая для request-ошибок содержит **URL**. В `sign_out` URL содержит `token=<access_token>` (`twitch.rs:817–829`), а лог-редакция ищет только подстроки `access_token`/`refresh_token` (logging.rs:177) — токен может попасть в журнал при сетевой ошибке выхода.
2. Чат Twitch идёт по plain TCP (F-16) — только чтение публичного чата, но всё же открытый трафик.
→ (1) В `sign_out` не логировать сырую ошибку (`log::warn!("Twitch: не удалось отозвать доступ")`), либо в `http::send` вырезать query из URL ошибки; расширить `looks_like_secret` (например, `token=`, `Bearer `, длинные hex/base64-фрагменты). (2) wss-IRC.
→ Проверка: unit-тест на редактирование строки с `token=`; сетевой сбой выхода → лог без токена.

**F-29 (P2) — Обработка ошибок: паники маловероятны.**
В `app.rs` нет `.unwrap()/.expect()`; в production-коде остальных модулей `unwrap/expect` практически отсутствуют (все найденные — в `#[cfg(test)]`: config.rs:582+, twitch.rs:1150+, queue.rs:395+, json.rs:52+ и т.д.). Есть паника-хук (logging.rs:212–218), `windows-subsystem="windows"` (main.rs:7), окно с ошибкой при фатальном сбое eframe (main.rs:63–68). `read_to_string`/`parse` обёрнуты в `Result`, битый config/queue переименовывается (config.rs:432–458, queue.rs:350–353).
→ Достаточно. Замечание: при `panic="abort"` (F-26) паника не будет разматываться — хука достаточно.

**F-30 (P2) — Диагностика отсутствует.**
Нет ни FPS/кадрового времени, ни счётчиков CPU/очередей, ни «почему repaint». Поэтому такие вещи, как F-1/F-2, годами не видны.
→ В debug-сборке (или скрытой вкладке) показывать: кадры/с, время кадра, длину каналов, число pending-событий, число потоков; логировать «busy reason» при смене. Дешёво и окупается.

## 6. Риски и потенциальные баги

**R-1 (высокий, воспроизведён) — Рассинхрон «окно видимо, `window_visible=false`».** Второй экземпляр EXE (`main.rs:29–32, 142–144`) показывает окно напрямую через `window_ops::show_from_tray()`, не уведомляя работающий процесс. Итог: вечный busy-repaint 6,7 кадр/с (замер 1,87 % CPU) и возможные странности с «Свернуть в трей»/закрытием. Лечится F-2/F-1.

**R-2 (высокий) — `update()` может не вызываться вовсе при реальном скрытии окна.** Кнопка «Свернуть в трей» в настройках использует `ViewportCommand::Visible(false)` (app.rs:2428–2435) — это не тот путь, что `hide_to_tray()`; по комментарию window_ops.rs:1–6 eframe в этом случае не шлёт обновлений, поэтому `poll_tray`/`poll_twitch`/`poll_music`/`poll_normalize` не работают, пока окно не покажут из трея напрямую. Т.е. два механизма скрытия ведут себя по-разному — унифицировать (F-2).

**R-3 (высокий) — Латентность/потеря реакции UI при видимом простое.** Из-за отсутствия waker'ов (F-3) события EventSub/трея/музыки обрабатываются только в кадре. В худшем случае заявка на трек не начнёт загружаться, а статус EventSub/тосты не обновятся, пока стример не подвинет мышь. Сейчас маскируется постоянным repaint'ом в трее.

**R-4 (средний) — «Перезапустить аудио» раздваивает аудиодвижок** (F-14): старый клон `AudioEngine` жив в `playback::Playback` EventSub-сервиса; звуки идут через старый поток, громкость/стоп — через новый; на устройстве два потока.

**R-5 (средний) — Музыка после смены аудиоустройства.** `audio.rs:283–314` отслеживает смену устройства только для звуков наград; `music/player.rs` — нет. При переключении (у пользователя в журнале 4 переключения за сессию: Loop-back ↔ Analogue) музыка может продолжать играть «в никуда»/на старое устройство до ошибки.

**R-6 (средний) — Диск: 234,6 МБ брошенных `_MEI*`** (F-20). Без очистки растёт на ~29 МБ за каждый таймаут загрузки/обновления yt-dlp (таймауты 20/60/120 с уже предусмотрены, значит инциденты реальны — 8 каталогов за 2 дня).

**R-7 (средний) — Очередь заявок не переживает перезапуск/краш** (F-23): `restore_queue=true` обещает восстановление, `queue.json` не пишется. Зритель оплатил баллы, трек мог не сыграть; статус активации остаётся невыставленным (завершение обрабатывается только по событиям музыки).

**R-8 (низкий) — Оверлей: локальный DoS/висящие потоки** (F-17). Клиент, подключившийся к 127.0.0.1:8770 и не отправивший запрос, вешает поток навсегда (нет read timeout); каждый запрос — новый поток.

**R-9 (низкий) — Возможная утечка access-токена в журнал** при сетевой ошибке `sign_out` (F-28): `reqwest::Error` содержит URL с `token=...`, redaction ищет `access_token`.

**R-10 (низкий) — EventSub-подписки могут накапливаться** при частых переподключениях (F-18); лимит Twitch 300 подписок/клиент. Сейчас сессия без переподключений, но при нестабильной сети стоит ограничить.

**R-11 (низкий) — Потеря последних правок настроек при аварийном завершении** в пределах 350 мс (дебаунс); и наоборот, серии записей при драге слайдера (F-21).

**R-12 (низкий) — Дубли poll'ов** (F-4) не вредят, но могут маскировать реальные ошибки (например, дважды обработанное событие, если бы poll был деструктивным; сейчас `try_iter` не деструктивен для статуса, но `take_errors` — деструктивен: вызов дважды подряд безопасен, т.к. второй опустеет; тем не менее лучше убрать).

**R-13 (низкий) — Единственный экземпляр и второй запуск**: `CreateMutexW(Local\...)` (main.rs:115–133) — на сессию пользователя, это ок; но показ окна вторым процессом идёт в обход трея (R-1).

## 7. Чек-лист проверки после оптимизаций

1. **Трей**: свернуть окно, 60 с без действий: `(CPU_end − CPU_start) / 60` должно быть < 0,3 % одного ядра (сейчас 4,2 %+).
2. **Окно на «Наградах», простой**: 60 с → < 0,3 % (сейчас 0,4–0,6 %).
3. **Рассинхрон**: запустить второй EXE → окно открылось → 30 с → не должно быть роста CPU (сейчас +1,9 %).
4. **Вкладка «Журнал»/«Музыка»**: 60 с на каждой → < 0,5 % (сейчас ~1,5–2 %).
5. **Латентность**: при простое видимого окна активировать награду «Трек по заявке» → в журнале «Музыка: заявка … в очереди» ≤ 1–2 с; привязанный звук играет независимо от UI (проверено кодом: playback в EventSub-потоке).
6. **Аудио**: 60 с без воспроизведения при двух открытых потоках → цель один `cpal_wasapi_out` (или 0 при ленивом потоке); переключить устройство Windows при играющей музыке → музыка продолжает играть на новом.
7. **Диск**: после 10 запусков/неудачных загрузок `tmp` не растёт; сразу после старта `_MEI*` нет; старт по журналу ≤ 1,4 с до «yt-dlp …».
8. **Память**: WS в простое ~55–65 МБ; после проигрывания трека возврат к < 100 МБ в течение ~1 мин (сейчас PCM/предзагрузка могут держать арену); отсутствие роста private на 30-минутном простое (проверено: стабильно).
9. **Журнал**: 1 ч работы — 0 строк «Чат: соединение закрыто»; лог не содержит `token=`/`Bearer`.
10. **EXE**: размер после `panic="abort"`/без `default_fonts` — ≈10,0–10,2 МБ; запуск, окно, звук, EventSub — без изменений.
